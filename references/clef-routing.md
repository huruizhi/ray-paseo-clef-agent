# Clef 候选路由

初始化发现决策服务、首次分配或重新选择执行组合时读取本文件。管理者构建候选和落实执行，Clef 从中选择具体组合。任务角色、执行程序、模型和决策服务是四个独立概念。

## 服务初始化

优先复用用户已选择的本地服务。核验服务地址、模型 ID 与实际响应，把 endpoint、模型版本或 digest、运行时和路由 schema 版本纳入本次记录。此前已确认的配置先现场核对，只追问缺失或变化的信息。部署、更新和下载权重由具体部署请求授权。

Ollama 配置示例为 `http://localhost:11434/v1/systemone` 和 `clef-flash:9b-mxfp8`；实际使用前核验当前主机的服务地址和模型 ID。可通过 Ollama 的模型列表、模型详情和最小决策请求核验。服务健康与候选 Agent 的调用能力分别记录。

Clef 需要 backbone 与 joint schema head 共同参与决策。使用已有支持决策的运行时；自定义适配须验证完整路径。Ollama 原生决策入口见 [Decision 文档](https://docs.ollama.com/capabilities/decision)，官方 PyTorch 实现见 [模型仓库](https://huggingface.co/Cloudflare/clef-flash/blob/main/joint_schema_model.py)。已有服务能正常完成决策时，直接进入候选路由。

## 构建输入

每个候选 ID 对应初始化快照中的完整执行配置。精确 provider、model、推理档位与执行设置保存在快照中，执行时按 ID 查表。`state` 提供判断需要的信息：

- 本阶段目标、任务类型、交付物和可操作的验收标准。
- 工具、上下文、语言、资料访问和工作区要求，以及用户指定的组合约束。
- 候选的执行程序、精确模型与推理设置、能力说明及其来源；已验证成功的任务、已知限制和未知项。
- 最近执行结果、具体失败证据、现有会话的上下文价值和切换代价。
- 路由目标：质量优先；满足本阶段质量要求后，再比较预计总耗时和可核对成本。没有可靠数据的属性标注未知。

候选先经主技能的硬条件过滤。用户指定一个合格组合或只剩一个候选时，直接执行并记录来源；零候选时处理缺口。两个及以上时调用 Clef。候选较多时，先依据用户偏好和已知工具/任务适配证据缩小清单，记录筛选依据，并遵守当前接口的选项上限。

编码、研究和写作使用各自验收标准。Clef 的输入应描述本阶段真正要完成的工作，例如“收集官方来源并解释冲突”或“按已通过评审的大纲成稿”，而不是只提供“困难研究/简单写作”。候选能力说明区分实测、用户偏好和待验证判断；避免根据模型名字编造强弱、价格或性能。

## 直接选择候选

用一个 `choice` 问题选择完整组合，避免分别选择程序和模型造成无效配对。候选 ID 在请求期间保持不变，每项 criteria 由候选摘要生成；保留有区分度的能力、限制和证据，完整配置仍可由快照追溯。

下面只展示请求结构，描述中的能力证据为示意，实际发送时由初始化结果替换。`model` 必须使用服务实际报告的决策模型 ID；候选 ID 必须与本次快照完全一致。

```json
{
  "model": "clef-flash:9b-mxfp8",
  "state": {
    "goal": "修复一个跨文件回归问题并补充行为验证",
    "stage": "定位根因并实现修复",
    "acceptance": ["原复现通过", "相关行为检查通过", "保留现有接口"],
    "priority": "quality_first_then_time_and_cost",
    "observation": "现有测试只能复现失败，根因尚未定位。",
    "candidate_snapshot": "本次初始化生成的候选快照",
    "constraints": ["候选均已通过工具、授权和配置兼容性检查"],
    "history": []
  },
  "questions": {
    "assignment": {
      "type": "choice",
      "instructions": "Select the candidate execution bundle best suited to meet this stage's quality requirements. Use supplied capability evidence and limitations. Compare total time and known cost only after quality requirements are met. Unknown performance or cost is unknown, not better. Return one candidate ID.",
      "criteria": {
        "candidate_01": "执行程序A、模型A、中推理；支持本仓库读写和测试。已通过若干局部修改任务，跨文件根因定位能力尚未验证。成本与延迟未知。",
        "candidate_02": "执行程序B、模型B、高推理；支持本仓库读写和测试。已有相近跨文件回归定位及修复的验收记录。成本与延迟未知。"
      }
    }
  }
}
```

这一次调用本身只产生选择；管理者随后按快照把选中 ID 对应的精确配置传给 Paseo。用户允许时可先用不创建 Agent 的路由样例验证协议，再让首个实际任务验证执行能力。

## 调用、校验与执行

使用可用 HTTP 客户端把请求发送到已核验的 `/v1/systemone`，设置有界超时，保留服务已有身份验证并去除日志中的凭据。保留实际请求与响应证据，未发出请求时不能声称由 Clef 选择。

读取 `answers.assignment.choice` 和 `probabilities`，检查：

1. choice 是本次提交的候选 ID，概率键恰好覆盖这些候选。
2. 概率均为有限非负数且不超过 1，总和在数值误差内接近 1。
3. 选中项对应最大概率之一；并列时按质量证据、已有会话价值及用户偏好处理，记录依据。
4. 选中配置仍属于本次允许集合，目标主机和工具仍可用。

有效结果在授权范围内落实到 Paseo；不要把 `assignment` 再映射为 routine/reasoning 后另选模型。用户指定、单一候选、实际 Clef 选择、管理者覆盖与故障降级分别记录。

缺失关键任务信息时，管理者先查资料并向用户补充沟通；无需把 `clarify` 混入执行候选。候选都不适合时回到初始化，不强制选一个。服务超时或异常响应时按主技能的故障规则处理，报告降级；用户要求 Clef 必须参与时，恢复服务后继续。

## 反馈与改进

概率是本次给定候选间的选择分布，不能解释为任务成功率，也不能证明其他候选能力不足。变更候选集合、描述、schema 或模型量化都会改变分数；原始 top probability 和接口 confidence 分别保存。

质量未知的候选先在有价值且可验收的阶段积累记录。对尚未验证的选择保留管理者复核；没有质量或兼容性依据时，不能只因主观偏好覆盖有效选择。记录覆盖原因以便审查路由是否真正影响执行。

按同类阶段的首次验收通过率、缺陷严重程度、返工和升级评估质量，再比较总耗时及可归因成本。固定 schema、模型版本与候选描述，在留出的任务上验证后再采用数字阈值。跨版本或量化后重新核验，避免凭空设置通用概率门槛。

阶段结束、出现新诊断或候选失效时，将新证据反馈给 Clef，重新选择保留或更换组合。模型升级属于重新选择的可能结果，按工具实测兼容性与现有授权执行；环境故障先恢复环境。
